Le protocole HTTP

HTTP est le protocole applicatif du Web : un client envoie une requête, un serveur renvoie une réponse, le tout au-dessus de TCP.

Principe

  • Créé en 1989 par Tim Berners-Lee avec le HTML. HTTP/1.1 (1999, RFC 7230 à 7235) reste le plus répandu ; HTTP/2 date de 2015.
  • Clients : Firefox, Chrome, Lynx, curl, wget. Serveurs : Apache, Nginx, IIS, Lighttpd.
  • Le client ouvre une connexion TCP (port 80), émet une requête, le serveur répond. Les connexions peuvent être persistantes (Keep-Alive).

Nommage et format des messages

URL : http://hôte[:port][/chemin[?requête]], par exemple http://opale.iut-clermont.uca.fr/info/wiki/doku.php?id=reseaux2.

Un message contient : une ligne de départ, des en-têtes, une ligne vide (\r\n), un corps optionnel.

Requête GET

»GET /test.html HTTP/1.0 Host: opale.iut.uca.fr Accept: text/html, text/plain, */* User-Agent: Lynx/2.8.8
  • GETMéthode : récupérer une ressource.
  • /test.htmlURI demandée.
  • HTTP/1.0Version du protocole.
  • Host: opale.iut.uca.frEn-tête : serveur visé (hébergement virtuel).
  • Accept: text/html, text/plain, */*Formats acceptés par le client.
  • User-Agent: Lynx/2.8.8Identité du client.

Chaque ligne se termine par \r\n ; une ligne vide termine l’en-tête.

Réponse du serveur

«HTTP/1.1 200 OK Content-Type: text/html Content-Length: 48 Connection: close
  • HTTP/1.1Version.
  • 200Code d’état.
  • OKPhrase de cause.
  • Content-Type: text/htmlType MIME du corps.
  • Content-Length: 48Taille du corps en octets.
  • Connection: closeLe serveur ferme la connexion après la réponse.

MéthodeRôle

  • Cache : If-Modified-Since renvoie 304 Not Modified si la ressource est inchangée ; Pragma: no-cache l’évite.
  • Cookies : HTTP est sans état ; un cookie associe un identifiant de session au client.
  • Authentification : Basic (mot de passe en clair, à proscrire hors HTTPS) ou Digest (hash).

HTTPS

HTTPS = HTTP + TLS/SSL, port 443. Il apporte authentification du serveur, confidentialité et intégrité.

  1. Certificat
    Le serveur présente un certificat X.509 (identité + clé publique) signé par une autorité de certification.
  2. Vérification
    Le client contrôle la signature avec la clé publique de l’autorité, intégrée au navigateur.
  3. Clé de session
    Le client chiffre une clé secrète avec la clé publique du serveur ; le serveur la déchiffre avec sa clé privée.
  4. Échanges chiffrés
    La cryptographie symétrique, plus rapide, protège ensuite toutes les données.

Proxys et TP

Un proxy (mandataire), comme Squid, offre un cache partagé, du filtrage, du contrôle d’accès et de la journalisation. TP : écrire un serveur HTTP minimal en Shell avec des sockets ou netcat.
